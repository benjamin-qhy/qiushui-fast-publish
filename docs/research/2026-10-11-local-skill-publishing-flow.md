# 本地 Skill 调用 MultiPost 的发布流程：现状与设计决定

日期：2026-10-11。本文记录实施前代码的流程梳理及用户逐轮确认的设计决定。已实施项目内 Skill、本机桥接、任务回执及小红书动态图文的“准备内容”适配，并完成真实闭环验证；其他类型和暂存／直接发布仍待适配与验证。最新实施证据见[Agent 仅调用 CLI 的验收记录](../validation/2026-10-11-rednote-agent-only.md)，早期桥接页测试见[本机验收记录](../validation/2026-10-11-rednote-local-chain.md)，平台入口范围另见[平台与内容类型清单](../platform-publishing-capabilities.md)。

## 运行职责（按用户最新要求实施）

浏览器控制只用于开发排错与验收。生产 Skill 的所有步骤只需要文件与 CLI/HTTP，平台页面打开、上传、填写和字段核对全部由 MultiPost 扩展执行。一次性安装配对由安装人员完成，不属于每次内容任务。

```text
Agent + Skill → 本机 CLI/API → 持久任务队列
                                ↑ 插件后台自动领取
                         MultiPost → 平台页面
                                ↓ 插件核对并回传证据
Agent + Skill ← 状态查询 ← 持久回执
```

## 用户期望的链路

```text
本地内容包（标题、正文、标签、图片／视频／音频）
  → 调用 Skill，识别内容类型
  → 读取该类型已配置的平台
  → 检查素材与账号状态
  → 将内容交给已安装的 MultiPost 扩展
  → 逐平台填写、暂存或提交
  → 逐平台返回有证据的结果与下一步
```

已确定采用**一个公共 Skill 入口、四种类型校验与组装规则**：动态、文章、视频、播客共用平台选择、预检、任务追踪和结果汇总，分别映射到 `DynamicData`、`ArticleData`、`VideoData`、`PodcastData`。首版 Skill 位于项目根目录 `skills/multipost-publish/`，首个执行适配是小红书动态图文；其他类型目前明确拒绝执行并提示尚未验证。

## 实施前代码实际走的链路

```text
网页 window.postMessage
  → 内容脚本检查网页来源是否受信任
  → chrome.runtime.sendMessage(PUBLISH, SyncData)
  → 后台暂存单份 currentSyncData，立即回 received，打开 publish.html
  → 弹窗取回 SyncData，尝试 fetch 素材 URL 并处理内容
  → 弹窗发送 PUBLISH_NOW
  → 后台按平台打开标签页、等待加载、注入对应 injectFunction
  → 平台函数填写／上传；部分函数尝试点击发布或调用草稿接口
  → 后台回传标签页列表，弹窗显示“发布完成”
```

最后一步仅证明后台返回了标签页列表，**不能证明平台内容已填写、已暂存或已发布**。平台注入函数的返回类型为 `Promise<void>`，注入调用未汇总逐平台结果；部分函数仅在控制台记录错误。详情见[网页桥接](../../src/contents/extension.ts)、[后台消息处理](../../src/background/index.ts)、[弹窗处理](../../src/tabs/publish.tsx)、[注入流程](../../src/sync/common.ts)。

## 实施前能力与缺口

| 环节 | 当前能力 | 对本地 Skill 的影响 |
| --- | --- | --- |
| 内容类型 | `SyncData` 定义四类载荷，四张平台表提供发布函数 | 可共享一套入口，须按类型校验并构造载荷 |
| 平台配置 | 仓库保留动态、文章、视频选择组件及其本地存储键 `dynamicPlatforms`、`articlePlatforms`、`videoPlatforms`，但当前入口未引用这些组件；扩展弹窗实际打开 `multipost.app/dashboard/publish`，其平台选择状态不在本仓库内。`PLATFORMS` 只返回全量平台注册表 | 不能把旧组件的本地存储当成现用配置；Skill 目前读不到“该类型已选平台”，播客也没有仓库内选择界面 |
| 本地调用 | 已有受信任网页的 `postMessage` 桥接，清单声明 `http://localhost:2663/*` 可外部连接；仓库没有供本地 Skill 直接调用的 CLI、HTTP 发布端点、Native Messaging 或 `onMessageExternal` 发布处理 | 已补充仅监听本机的任务 API，扩展后台经一次性配对后自动领取任务；Agent 只用 CLI/HTTP，浏览器须安装并运行扩展 |
| 素材 | `FileData` 使用可 `fetch` 的 URL；弹窗会复制为 blob URL | OS 本地路径不能直接作为现有载荷；文件缺失或读取失败时，现有流程可能继续执行 |
| 登录 | 仅 16 个账号键有刷新 getter，刷新页可报告部分账号的未登录／错误；发布流程没有强制登录预检 | 缓存为空或过期只能判为“未验证”，不能直接断言“未登录” |
| 提交动作 | 部分平台可点击发布，部分只填表单或保存草稿；具体行为见各平台处理函数 | 不能用 `isAutoPublish` 一个布尔值统一代表“已发布” |
| 结果 | 弹窗的“发布完成”以标签页回调为依据；平台函数没有统一回执 | 需要新增逐平台状态、证据和错误回传，才能准确通知 Skill |
| 并发 | 后台仅有一份 `currentSyncData` | 并发调用可能串内容；可靠链路需要任务 ID 和串行化或隔离 |

旧组件、现用入口和账号缓存代码见[动态设置](../../src/components/Sync/DynamicTab.tsx)、[文章设置](../../src/components/Sync/ArticleTab.tsx)、[视频设置](../../src/components/Sync/VideoTab.tsx)、[当前弹窗入口](../../src/popup/index.tsx)、[账号管理](../../src/sync/account.ts)。素材和结果处理见[载荷定义](../../src/sync/common.ts)及[发布弹窗](../../src/tabs/publish.tsx)。

`isAutoPublish: false` 也不能直接解释为“只准备”：例如部分文章处理函数在此条件下会保存草稿。首版必须按“平台 + 内容类型 + 目标动作”适配，并检查现有函数的实际副作用；不能只改布尔值后复用全部处理函数。

## 目标链路

```text
Skill 接收本地内容包
  → 判定唯一内容类型、检查必填字段和每个文件的可读性
  → 获取该类型已选平台及平台能力，形成逐平台计划
  → 检查登录：已验证／未验证／验证失败，不凭旧缓存作保证
  → 为本次调用生成任务 ID，并把本地素材安全交给浏览器
  → 向扩展提交任务；扩展按平台分别执行
  → 每个平台返回阶段、证据、错误和可重试建议
  → Skill 汇总：已填写／草稿已确认／发布已确认／需要处理／结果不确定
```

状态必须由平台侧证据支持：“已填写”需要检查页面必填字段；打开编辑页或点击按钮只说明动作已尝试；明确保存回执才能称“草稿已确认”；平台发布回执或可核对的作品 ID／URL 才能称“发布已确认”。没有回执时保留“结果不确定”，避免盲目重发。必需素材缺失时整次任务在执行前停止；单个平台登录或执行失败时，该平台停止，其他平台继续。账号无法确认时报告“未验证”，不能断言“未登录”。

## 已确认的第一轮决定

1. **Skill 形态**：一个公共 Skill，内含动态、文章、视频、播客四类独立的校验与载荷适配。
2. **平台配置来源**：首版使用本地配置文件，按内容类型分别列出目标平台。现用网页的选择状态不作为首版配置来源。
3. **目标动作**：每次任务可明确指定准备、暂存草稿或直接发布；未指定时仅准备内容供检查。
4. **运行位置**：先在当前电脑完成可验证的端到端链路，再决定如何给其他 Agent 或电脑复用。

这里的“当前电脑的完整链路”是指：本机内容文件由 Skill 读取和校验，经本机桥接交给已安装并运行的 MultiPost 扩展，扩展在目标平台执行所指定的动作，再把每个平台有证据的阶段、失败原因或不确定状态传回 Skill。验收须覆盖一次真实平台任务，从输入、素材读取、账号检查、插件执行到结果回传；默认动作是准备，不因此自动公开发布。跨电脑安装和通用打包放在后续阶段。

## 已确认的第二轮决定

1. **本机桥接**：原方案用本机桥接页交付任务；用户随后明确其他 Agent 不能控制浏览器，因此已改为一次性配对后由扩展后台自动领取本机任务。Agent 只提交与查询 CLI/HTTP；素材在领取时核对哈希并转换，不能把 OS 路径直接塞入现有 `FileData`。
2. **失败范围**：必需素材缺失时不启动任何平台；某个平台未登录或执行失败时，只停止该平台，其他平台继续；无法确认登录时标为“未验证”。
3. **结果证据**：已填写须检查页面必填字段；草稿须有平台保存回执；发布须有平台回执或可核对的作品 ID／URL；提交后缺回执标为“结果不确定”，先核查，不盲目重发。
4. **验证顺序**：先以一个内容类型、一个平台做真实端到端验证，再扩展到四类内容及已配置平台。对每个平台分别记录已验证的动作和结果证据。

## 已确认的第三轮决定

1. **内容输入**：每份内容是一个目录，元数据文件写内容类型、标题、标签等，正文和素材用该目录内的相对路径引用；调用 Skill 时给出目录路径。
2. **不支持目标动作**：在执行前标明对应平台“动作不支持”并跳过，不擅自降级为填写、草稿或发布。
3. **中断与不确定结果**：持久记录任务 ID 和逐平台进度。恢复时先核查原任务及平台页面；对可能已提交的平台不自动重发。
4. **逐平台差异**：内容包的通用字段为默认值；可在同一内容包内为特定平台覆盖标题、分类、原创声明等字段，执行前校验覆盖值。

## 已确认的第四轮决定

1. **未验证动作**：尚未通过真实平台验证的自动暂存或直接发布动作不执行，逐平台报告“尚未验证”；该平台可以保留在配置中。已有代码入口不等于已验证的动作。
2. **人工处理与恢复**：遇到扫码登录、验证码或平台要求补填信息时，仅暂停受影响的平台，保留其页面和原任务，给出具体处理提示；处理完成后继续原任务，其他平台照常执行。
3. **临时平台范围**：一次调用可以只选择该内容类型已配置的平台子集；新增目标平台须先修改平台配置。配置为空或子集含未配置平台时，在打开平台页面前提示配置问题。

## 首版输入与配置草案

一次调用指向一个内容目录，例如：

```text
post-2026-10-11/
  content.yaml
  body.md
  cover.jpg
  images/
    01.jpg
```

```yaml
# content.yaml；平台键使用插件 InfoMap 中的精确名称
type: ARTICLE
title: 示例标题
bodyFile: body.md
cover: cover.jpg
images:
  - images/01.jpg
tags: [示例]
overrides:
  ARTICLE_ZHIHU:
    title: 知乎标题
    original: true
```

Skill 在本机读取按内容类型分组的平台配置。实际位置为 Skill 内 `config/platforms.yaml`；内容目录不自行决定发布目标，逐平台覆盖只改变内容字段。Skill 必须确认所有引用文件存在、可读，路径不越出内容目录，再转换为插件所需的 `DynamicData`、`ArticleData`、`VideoData` 或 `PodcastData`。本文路径和文件名是实施草案，可在实现时按本机环境调整，业务规则不变。

## 执行与结果协议草案

1. Skill 读取内容包、目标动作与该类型平台配置，构成逐平台计划；无指定目标动作时为“准备内容”。可选平台子集必须包含在该类型的配置内。
2. 必需素材缺失或无效时，整个任务在平台操作前失败；单个平台不支持目标动作时标为“动作不支持”，未验证的自动暂存或直接发布标为“尚未验证”，其余平台继续。
3. 本机 API 仅监听 loopback，Agent CLI 凭证与扩展执行器凭证分离。安装人员一次性配对后，扩展后台自动领取任务和通过哈希校验的素材，无需 Agent 操作桥接页；素材转换为任务内 data URL。
4. 插件为每个平台保留任务 ID、目标动作、执行阶段、证据、错误及编辑页／作品引用。打开标签页、填写、保存和提交分别记录，不能把消息“received”或标签页列表当作平台结果。
5. Skill 展示逐平台结果：`已填写`、`草稿已确认`、`已提交待审核`、`发布已确认`、`动作不支持`、`尚未验证`、`需要处理`、`执行失败`或`结果不确定`。需要处理时附登录／验证码／缺少平台必填信息等原因，保留原任务并支持继续；结果不确定时先核查，不自动重试提交。作品 ID／URL 必须能够核对具体状态；仅有 ID 或提交成功提示不足以断言已发布。

## 首版验收边界

- 在当前电脑上，用真实内容目录和一个已登录平台完成从 Skill 调用到插件页面操作、再到 Skill 结果回传的闭环。初次真实验证默认使用“准备内容”，检查页面必填字段后才能报告“已填写”。
- 同时验证缺失素材在操作平台前停止、未登录平台给出可操作提示、单个平台失败不掩盖其他平台结果、页面中断后可查到原任务。
- 四种内容类型都要有明确的输入校验和平台映射；逐平台的暂存／直接发布动作只有在该平台具备相应能力与可核对证据后，才进入已验证范围。

## 实施顺序

1. 建立公共 Skill 的内容目录规范、四类校验及本机平台配置读取；输出逐平台计划。
2. 实现本机桥接、素材传递和持久任务记录，并在插件中补充逐平台结果协议；首版任务串行执行，避免现有单份 `currentSyncData` 串内容。
3. 选择一个内容类型和一个当前电脑可用的平台，适配安全的“准备内容”动作与字段核对，完成真实闭环。
4. 验证缺失素材、登录暂停、单个平台失败及中断恢复，再扩展四类内容和配置的平台。
5. 对每个平台分别适配暂存／直接发布和结果核查，完成真实验证后开放相应自动动作。平台明确处于审核阶段时报告“已提交待审核”；平台确认发布完成时才报告“发布已确认”。

上述为已确认的整体设计与实施顺序。首版实际使用 Skill 内的 `config/platforms.yaml`，支持 `content.yaml`／`content.json`；本机运行目录为项目忽略的 `.multipost-local/`。小红书已验证动作和剩余范围以验收记录为准，不能把一个平台的成功扩大为所有平台注册表的成功。当前选择均可按首版验证结果调整，未达到建立 ADR 的条件。
